大多数多智能体（Multi-Agent）Demo 止步于“多个角色在一个聊天室里互相接话”。在日常写代码时，这种模式很快会暴露出三个致命问题：**上下文迅速膨胀并互相污染**、**多个 Agent 同时改同一份工作区导致冲突**，以及**复核者被执行者的自述话术“说服”而放水**。

[Lemma](https://github.com/wangchneyu/Lemma-pi-durable) 是我基于 `@earendil-works/pi-durable` 和 SQLite 构建的本地多智能体协作系统。这篇文章不谈概念，只复盘我在设计它时最核心的几个工程取舍。

## 为什么叫 Lemma（引理）

在数学证明里，**引理是用来支撑后续命题的辅助命题**。面对一个复杂的结论，通常需要先建立几条各自成立的引理，再把它们安全地组合起来。

Lemma 把这套思路映射到 coding 场景的 Agent 协作上：把一个复杂开发目标拆成**有文件边界、有前置依赖、有明确验收标准**的子任务，交给独立上下文的成员完成，跑完配置的编译器/测试检查、保留证据，再把通过验证的产物交给下游或人工合入。

## 1. 信息隐藏与结构化交接

多 Agent 协作最容易掉进的坑是“共享完整聊天记录”。如果上游调试了十轮弯路，把整段历史原封不动塞给下游审查员，不仅浪费上下文窗口，还会把早期假设错误带进后续推理（级联幻觉）。

在 Lemma 中，每个成员持有自己独立的持久化会话：

- **上下文按任务裁剪**：默认只向成员交付当前任务定义、直接前置依赖、上级目标以及必要的项目背景；追问同一个成员时复用其 `session_id`，未变化的大段资料只传引用。
- **结构化交付协议**：派工可以声明 `structured: true`，要求交付 `lemma.delivery.v1` 结构化结果（结论、数据、证据来源、产物引用与未完成项）。下游成员通过 `inputs: [{ result_id, field }]` 仅接收需要的字段，原文留在持久化存储里，总控需要核对细节时再通过 `read_result` 按 `result_id` 分页读取。

## 2. 路径契约、ACI 工具与代码盲审

如果只靠提示词约束“不要改其他模块的文件”，模型在复杂改动中依然可能越界。Lemma 用三道硬边界代替纯口头约定：

1. **路径契约（`scope`）**：任务支持声明 `scope: { allow, forbid }`。对于 API 编码成员，写入文件前会实时拦截越界路径；任务收尾与验收阶段还会针对 `git` 实际改动再做一次硬校验，以此支撑“契约先行 + 实现与测试分流”。
2. **专用只读代码工具（ACI）**：API 编码与审查成员内置 `list_files`、`outline_file`、`find_symbol`、`search_code` 与 `git_diff`，先拿文件结构大纲和符号定义，再对照改动基线查看补丁差异，减少盲目整文件读取。
3. **独立盲审（`reviewer.blind: true`）**：当任务配置 `reviewer: { member, model?, blind: true }` 时，复核阶段会剥离执行者的主观自述文本，让审查员只面对需求契约与客观的 `git_diff` 做出判断，用来对抗大模型常见的迎合偏见（Sycophancy）。

此外，复核结论必须绑定当前的 `result_id` 和代码提交版本——一旦执行者返工改了代码，旧的“通过”结论自动失效。

## 3. 复杂度自适应拓扑（L0 / L1 / L2）

并非所有改动都需要“规划 → 实现 → 盲审 → 集成”全套流程，小任务套用重编排只会白白消耗轮次和延迟。Lemma 按耦合度与风险自适应选择协作拓扑：

| 级别 | 适用场景 | 协作路径 |
| :--- | :--- | :--- |
| **L0** | 单点小改动、简单问答 | 总控或单兵成员快路直达，不做多余编排 |
| **L1** | 中等风险代码改动 | 执行成员完成改动后进入独立盲审双人闭环 |
| **L2** | 多模块并行与高风险开发 | 契约先行 → 独立 Git worktree 并行实现/测试 → 联合集成验证 → 人工确认应用 |

在 **L2** 场景下，成员的改动默认落在各自独立的 Git worktree 中，互不踩踏。多个成员验收通过后，不会直接覆盖主工作区，而是通过 `integrate_changes`（或 `/integrate create`）在独立的集成工作副本里合并 2–8 项改动并运行 `autonomy.checks` 联合检查；遇到合并冲突或跨模块测试失败时，再用 `repair_integration` 在独立修复副本解决并重跑全部检查。只有检查全部通过、且人眼 `/diff` 确认后，才执行 `/apply` 落回主目录——**系统绝不擅自静默 `git commit`**。

## 4. 持久化恢复与双入口控制

长任务最怕中途断网、模型超时或终端关闭。Lemma 基于 `@earendil-works/pi-durable` 用 SQLite 持久化对话消息、任务分工表、依赖队列和检查点：

- **精细恢复**：任务受阻后，不必从头重跑已验收的前置工作，可以直接 `/task inspect` 查看现场，用 `/task resume`、`/task supply` 补充资料或 `/task reassign` 换人接手原工作分支。
- **并发与暂停控制**：支持 `/workflow pause` 暂停后续自动派发（已派出的任务继续收尾），状态跨进程重启保留；配合并发上限与每轮预算预留控制资源消耗。
- **终端 + 本地网页双入口**：终端复用 `pi-coding-agent` 与 `pi-tui` 提供原生流式交互与快捷键（会话切换、任务图面板），同进程启动的本地网页（`127.0.0.1:8787`）同步读取同一份持久化状态，展示任务看板、协作拓扑与用量统计。

## 边界与后续

Lemma 目前仍围绕本地开发与编码协作持续打磨，它明确的边界也很清晰：**工作区隔离和路径契约属于工程协作护栏，不等同于操作系统级沙箱隔离**；自动验证的能力上限取决于项目自身配置的检查脚本与人工 `/diff` 审查。
